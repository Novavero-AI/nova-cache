- **When `serialiseFromPath` or `withNarSource` fails to read an entry's status, a symlink's target, a directory's listing or a regular file, it throws `NarWalkError`, naming the access, the entry and the `IOException` beneath.** A failure in any of these four accesses escaped as GHC's bare `IOException`, so a caller could tell which access failed on which entry only by parsing GHC's text. Upstream's `PosixSourceAccessor` words each access its own way (`opening file '/d/tree/sub/locked': Permission denied`, `reading directory /d/tree/sub: Permission denied`), and a caller reporting failures as upstream does needs the access as a value. `WalkAccess` says which of the four failed (a file's open, size and reads are one access), `nwePath` is the entry's on-disk path, and `nweCause` is the `IOException` itself. `withNarSource` throws a file's read failure from the pull that reads it. Only an `IOException` is wrapped: an asynchronous exception passes through as itself, and whatever an `ExecBitResolver` throws arrives as thrown. A caller that catches `IOException` around a walk no longer catches these failures, which is why this is a major version.
