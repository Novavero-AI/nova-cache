- **A failed `withNarSource` pull stays failed: every later pull rethrows the same exception, as the xz, zstd and bzip2 sources' pulls do.** A pull that found a file shorter than the size it had read marked the source drained before it threw, so the next pull returned the empty chunk that marks a clean end, and a consumer that caught the failure and pulled again took a truncated archive for a complete one. Any exception raised while a pull runs now latches, asynchronous ones included, since a pull interrupted after its read consumed bytes it never returned leaves the archive as torn as a failed one. An asynchronous exception that arrives as a pull returns, after the source has moved past the chunk it was returning, is not latched, so a consumer must not pull again after an asynchronous exception. A pull after any other failure, such as a file that could not be opened, rethrows it as well, where it used to carry on from where the failure left the source. The file a failed pull held open is closed as the failure latches, not when the continuation exits.
