- **`serialiseFromPath` and `withNarSource` refuse a FIFO, a socket or a device with upstream's error, `file '<path>' has an unsupported type`.** The walk took every entry that is not a directory or a symlink for a regular file, through `doesFileExist`, which is true for anything that is not a directory, so the refusal written for these types never ran. `serialiseFromPath` then read the entry with `ByteString.readFile`, which reads anything that is not a regular file to its end of input: a FIFO with no writer, or `/dev/null`, archived as an empty regular file, and a device with no end, such as `/dev/zero`, was read without bound. `withNarSource` failed at the pull for the entry's contents, as a `NarWalkError` for a file read, after earlier pulls had returned part of the archive, and a socket failed both entry points as a file read. Each entry's type now comes from one `lstat`, classified by its file mode as upstream's `SourceAccessor::dumpPath` classifies it, and any type but a regular file, a directory or a symlink is refused before it is read; `withNarSource` refuses before its continuation runs. The refusal is an `IOException`, as the walk's other refusals of what it finds are, not a `NarWalkError`: no access failed, and no `IOException` lies beneath it. An entry that vanishes mid-walk fails the access that finds it gone, as a `NarWalkError`, unless the first read to find it gone is `defaultExecBitResolver`'s own status read, which throws its bare `IOException` as any resolver's failure arrives. Windows has no file mode, and its classification is unchanged.
