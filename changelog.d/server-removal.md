- **The server removes entries and NARs itself: `DELETE /<hash>.narinfo` removes an entry, `POST /reclaim` removes the NARs no narinfo names and the abandoned multipart uploads, and `GET /reclaim` lists what it would remove.** No request removed anything, and the one removal path, `reclaim-nars --delete`, ran on the host against the store directory and shared no lock with the server, so it raced the server twice: a narinfo that arrived after its listing, for a NAR past the minimum age, lost that NAR, as upstream's `nix copy` can send one after skipping a NAR the cache holds, and a NAR uploaded again after its listing was removed despite its new modification time. The README asked for no push in progress during a run. The server now orders its removals against its uploads through a gate each `FileStore` carries: a narinfo upload holds it, alongside other uploads, from the check of its NAR through its write, each rename into `nar/` holds it for the rename, and a reclaim or a narinfo removal holds it alone, the reclaim from its scan through its last removal. So a narinfo is never stored naming a NAR a reclaim removes, and a NAR that arrives during a reclaim lands after it. A removal waiting for the gate lets nothing new take it, so a stream of uploads cannot hold it off; uploads wait while a reclaim reads the store, and no request body is read under the gate. A run's rules are unchanged: a minimum age of two weeks by modification time (`?min-age-hours=N` sets another, and any other query is refused with 400), a narinfo that cannot be resolved or a store with NARs and no narinfo blocks the run with 409, and a removal that fails makes the answer a 500. All three requests need the write key, which can already replace any entry. `DELETE` leaves the NAR to the reclaim, which removes it once nothing names it, as attic's garbage collection reaps a NAR once no object refers to it. A narinfo uploaded for a path the cache holds replaces the entry, which lets a push store a smaller encoding of the same NAR, and the NAR it displaces is reclaimed the same way. Upstream ships no garbage collection for binary caches, so there is no server behavior to match, only its client's: `BinaryCacheStore::narFromPath` turns a missing NAR into `SubstituteGone`, which a substitution logs as a warning before it tries the next substituter (2.35.6), so a client holding a narinfo whose NAR was removed sees a miss, not a failure. One server serves a store directory.
- **`nova-cache-server reclaim-nars` exits nonzero, naming the requests that replace it.** The server removes NARs itself. The subcommand's name is still recognized so that a script running it stops: the server ignores arguments it does not know, and would otherwise start a second server over the store.
- **`FileStore` is abstract, made by `newFileStore` alone, and carries the store's gate.** `withoutRemoval` and `withRemoval` in `NovaCache.Store` hold it; `writeNar`, `writeNarStreaming` and `completeUpload` take it for their rename, and `removeNarInfo` and `NarInfoRemoveResult` are new. `fileStoreAt` goes, since its one caller was `reclaim-nars`, and `FileStore` loses its `Show` instance. In `NovaCache.Reclaim`, `scanStore` takes the clock it reads after its listings and lists the staged uploads into `StoreScan`'s new `scanStagedUploads`; `planStore`, `StorePlan`, `listReclaimable`, `reclaim` and `Reclaimed` are new. `NovaCache.Server` gains `storeNarInfo`, which checks, signs and writes a narinfo within one hold of the gate, `NarInfoWrite`, and `parseMinimumAge`. `stm` joins the dependencies, for the gate's `TVar`. These changes break the library's API, which is why this is a major version.
